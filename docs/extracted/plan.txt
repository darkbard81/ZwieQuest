01  /  DEVELOPMENT PLAN
프로젝트 개요와 문서 기준
기획의 중심은 복잡한 조작이 아니라, 스스로 여행하는 캐릭터를 관찰하고 관리하는 경험이다.
한 문장 정의
사용자가 접속하지 않아도 서버에서 모험을 계속하는 캐릭터를, 작은 횡스크롤 창과 자유 배치 도구 창으로 관찰·관리하는 웹 RPG.

만들려는 경험
캐릭터는 걷고, 몬스터를 만나고, 보물을 얻으며 자동으로 성장한다. 사용자는 갈림길에서 좌·우를 고르거나 모험 중 장비를 교체·판매한다. 아무 입력이 없어도 탐험은 멈추지 않는다. 핵심 반복은 출발, 이동, 사건, 분기, 귀환, 재출발이다.
Progress Quest는 자동 성장 관찰, 쯔바이 펫 모니터는 필요할 때만 개입하는 자율 탐험, 용사30은 단순한 표현으로 성장과 결과를 빠르게 전달한다는 비교 관점으로 참고한다. 원작의 규칙을 그대로 복제하는 계획은 아니다.

폐기·대체된 설정
동서남북 MUD식 맵은 좌·우 단방향 분기로 대체한다. 초기의 1024×768 논리 화면은 512×384 논리 화면과 DPR 2 버퍼로 구분한다. 16:9는 배경 원본 규격이며, 최신 게임 창의 4:3 비율과 동일한 의미로 취급하지 않는다.
온라인 1배·오프라인 4배는 앞선 설명의 예시였을 뿐 확정값이 아니다. 어느 쪽을 더 빠르게 할지도 이번 문서에서 임의로 결정하지 않는다.

03  /  DEVELOPMENT PLAN
핵심 모험 규칙
좌·우는 현재 지점의 두 전진 경로이며, 지리적 동·서나 되돌아가기 버튼이 아니다.
기본 반복
HOME → 출발 → 자동 이동 → 몬스터 / 보물 / 통과 → 다음 분기 → 이동 계속 → 막다른 길 → HOME

분기와 경로
분기마다 선택 가능한 다음 경로만 제공한다. 오른쪽을 선택한 뒤 다음 분기에서 왼쪽을 선택해도 이전 장소로 돌아가지 않는다. 화면의 좌우 걷기 방향과 서버의 진행 단계는 별개다. 진행 단계는 새 구간에 들어갈 때마다 증가한다.
제안: 완성된 거대 맵 대신 현재 구간과 다음 후보만 보관한다. 후보가 둘이면 선택 대기, 하나이면 자동 진행, 없으면 귀환한다. 사용자가 선택하지 않으면 마감 시 서버가 허용된 후보 중 하나를 선택한다. 좌·우 기본 확률과 사전 힌트의 제공 여부는 설정값으로 둔다.

귀환과 유지 데이터
제안: HOME 귀환은 위치·진행 단계·현재 사건만 초기화한다. 레벨, 경험치, 보유 재화와 획득 장비는 유지한다. 패배도 HOME으로 연결하되, 재화 손실이나 장비 파괴는 초기 범위에 넣지 않는다. HP 회복 방식과 출발 대기시간은 별도 결정 항목이다.
보상을 클릭해서 받아야 다음으로 진행되는 구조는 사용하지 않는다. 보상 표시와 레벨업 연출은 결과를 보여주는 기능일 뿐, 서버 진행을 승인하는 절차가 아니다.

04  /  DEVELOPMENT PLAN
성장·자동 전투·장비 관리
관찰의 재미는 남기고, 반복 조작과 전용 전투 스프라이트 요구는 최소화한다.
성장과 전리품
확정: 몬스터 처치와 보물상자 처리 후 서버가 경험치·재화·아이템을 지급한다. 경험치가 기준을 넘으면 레벨업을 자동 처리한다. 여러 레벨을 한 번에 통과하는 경우도 서버가 일관되게 계산한다. 경험치 곡선, 레벨 상한, 아이템 등급과 드롭 확률은 미정이다.
최소 전투 모델 — 제안
초기에는 HP, 공격력, 방어력과 일정한 행동 간격만 사용한다. 서버가 각 타격을 확정하고 승패와 보상을 처리한다. 회피·치명타·속성·스킬 트리·수동 공격은 필수 범위에 넣지 않는다. 복잡한 명중률 체계보다 장비 교체 전후의 차이가 드러나는지를 먼저 검증한다.
임시 검증식은 피해량 = max(1, 공격력 − 방어력)처럼 단순하게 둘 수 있다. 이는 밸런스 확정식이 아니라 전투·장비·성장 흐름을 연결하기 위한 제안이다. 캐릭터는 새 공격 모션 없이 짧은 흔들림, 밝기 변화, 효과와 피해 숫자로 반응한다.
모험 중 장비 교체·판매
상황
처리 규칙 — 제안
교체 요청
서버가 소유권과 장착 조건을 검증한 뒤 장비와 능력치를 한 번에 갱신한다.
진행 중 전투
교체 명령이 확정된 이후의 첫 미확정 타격부터 새 능력치를 적용한다. 이미 확정한 피해는 바꾸지 않는다.
판매 요청
아이템 삭제와 재화 지급을 하나의 트랜잭션으로 처리한다. 모험은 중지하지 않는다.
장착 중 판매
초기안은 먼저 해제해야 판매 가능하게 한다. 장착 상태에서 자동 해제·판매할지는 추후 결정한다.
중복 입력
요청 ID로 중복 처리를 차단한다. 처리 중 버튼 상태와 서버의 성공·실패 응답을 표시한다.
HP 장비 교체
최대 HP가 바뀌면 현재 HP는 새 최대치까지만 제한한다. 반복 교체가 무료 회복 수단이 되지 않게 한다.

방치가 막히지 않는 인벤토리
제안: 인벤토리 용량 때문에 모험을 멈추거나 아이템을 조용히 버리지 않는다. 정식 용량 정책 전까지 충분한 보관량과 초과 보관함을 두고 서버 저장 한도를 관리한다. 자동 판매는 사용자 요청이 없으므로 기본 기능으로 확정하지 않는다.

05  /  DEVELOPMENT PLAN
접속 상태와 시간 흐름
시간 배율은 캐릭터마다 적용한다. 웹페이지의 애니메이션 속도가 게임의 진행 속도를 결정하지 않는다.
시간 모델
확정: ONLINE과 OFFLINE은 서로 다른 진행 배율을 사용할 수 있다. 두 상태 모두 서버에서 사건이 실제로 발생한다. 제안: onlineRate, offlineRate, 온라인 선택 대기시간, 오프라인 선택 대기시간을 별도 설정으로 둔다. 어느 상태가 더 빠른지와 구체 수치는 미정이다.

로그인 쿠키가 남아 있다는 사실만으로 ONLINE을 유지하지 않는다. 연결 상태와 서버 기준 하트비트를 사용하고, 일시적인 단절에는 유예시간을 둔다. 다른 탭으로 이동하거나 마우스를 쉬었다고 즉시 로그아웃시키지는 않는다. 여러 탭·기기는 한 캐릭터의 접속 상태로 합산한다. 브라우저는 숨겨진 페이지를 정지하거나 폐기할 수 있으므로 클라이언트 종료 알림만 신뢰하지 않는다. [T2]
배율 변경 시 진행률 보존 — 제안
사건을 기다리는 도중 배율이 바뀌면 이미 소모된 게임 시간을 유지하고, 남은 게임 시간만 새 배율로 다시 예약한다. 이는 실행 중인 사건의 일정 변경이며, 비접속 기간의 모험 결과를 나중에 재생성하는 방식이 아니다.
remainingGameTime = max(0, previousRemaining - elapsedRealTime * oldRate)nextDelay = remainingGameTime / newRate

선택 대기는 사용자에게 제공하는 실제 응답 시간으로 별도 관리한다. 재접속을 반복해도 기존 선택 마감은 연장하지 않는다. 오프라인 전환 시 남은 대기를 줄일지는 정책으로 결정한다. 이전 예약은 버전 번호로 무효화해 중복 실행을 막는다.
서버 중단과 재접속
제안: 서버가 멈춘 동안은 게임도 멈춘다. 재시작 시 저장된 상태와 남은 대기에서 이어가며 중단 구간의 모험을 새로 만들어 보상하지 않는다. 재접속한 클라이언트는 현재 상태와 이미 저장된 사건 기록을 조회한다. 지연되어 이미 확정된 사건은 재계산하지 않는다.

창 복원, 표시 옵션. 시간 배율은 초기에는 운영 설정

창 구성과 세부 위치는 제안이며, 확정 요구는 GRID 초기 정렬과 이후 자유 배치다. 별도의 상점, 채팅, 거대한 지도 창을 필수로 추가하지 않는다. 접속 상태와 진행 배율은 제목 표시줄이나 상태 영역에 작게 표시한다.
GRID와 자유 배치의 연결
제안: 최초 표시 시 CSS Grid로 위치를 계산한 후, 모든 창의 사각형을 저장하고 전체를 자유 배치 좌표로 전환한다. 한 창만 Grid에서 빼면서 다른 창이 재정렬되는 현상을 피한다. 사용자는 이후 드래그로 이동하고 겹칠 수 있으며, 초기 배치 복원으로 정렬 상태에 돌아간다.
제목 표시줄에서만 이동을 시작하고 닫기·최소화 버튼, 입력창, 스크롤 영역은 제외한다. Pointer Events와 포인터 캡처로 드래그 도중 포인터가 창 바깥으로 나가도 동작을 이어간다. 크기 관찰에는 ResizeObserver를 사용한다. [T3, T4]
창별 동작 기준 — 제안
월드 창은 초기 단계에서 콘텐츠 512×384를 고정하고 이동·겹치기·최소화를 지원한다. 나머지 DOM 창은 이동과 크기 조절을 지원한다. 월드 창 크기 변경은 추후 4:3 유지 방식으로 확장한다. 창의 최소화나 크기 변경은 서버 모험을 일시정지하지 않는다.
레이아웃에는 창 ID, x·y, 폭·높이, 겹침 순서, 최소화 여부와 레이아웃 버전을 저장한다. 초기에는 기기별 localStorage를 사용한다. 화면 크기가 달라지면 제목 표시줄이 접근 가능한 위치로 보정하고, 서버 게임 데이터와 UI 배치 데이터를 분리한다.
접근성·입력 기준
좌·우 선택과 주요 버튼은 키보드로도 조작 가능하게 한다. 모험 중 확인창을 열어도 서버는 진행하므로 판매 대상과 현재 상태를 다시 검증한다. 창 포커스 전환은 모험 방향 입력으로 전달하지 않는다.

캔버스 규격과 배경 표시
512×384 게임 창과 16:9 배경 원본을 서로 다른 규격으로 관리한다.
항목
개발 기준
캔버스 콘텐츠
512×384 CSS px / 4:3. 제목 표시줄과 테두리는 별도라는 해석을 제안한다.
논리 좌표계
512×384. DPR을 곱해 게임 좌표까지 두 배로 늘리지 않는다.
렌더링 배율
기기 DPR을 자동 대입하지 않고 게임용 픽셀 비율 2로 고정한다.
드로잉 버퍼
기준 크기에서 1024×768 px. 창의 CSS 표시 크기와 별개다.
배경 원본
16:9의 2D Anime 이미지. 도로의 세로 위치와 원근감은 테마마다 유지한다.

Three.js는 setPixelRatio와 setSize를 조합해 논리 크기와 드로잉 버퍼 크기를 분리할 수 있다. 아래 기준에서는 CSS 크기를 별도로 지정하며 DPR을 중복 적용하지 않는다. [T1]
renderer.setPixelRatio(2);renderer.setSize(512, 384, false);canvas.style.width = '512px';canvas.style.height = '384px';

16:9 원본을 4:3에 표시하는 기본안
제안: 배경 높이를 384에 맞추고 좌우를 잘라 표시한다. 16:9 원본은 약 682.7×384가 되며, 512 폭의 창에는 가운데 75%가 보인다. 이 방식은 세로 비율을 보존하므로 상단 약 256은 원경, 하단 약 128은 도로 영역으로 유지된다. 배경을 4:3으로 강제 늘이지 않는다.
중앙 기준 좌우 약 85.3 CSS px의 여유를 짧은 스크롤에 사용할 수 있다. 실제 이미지 크기와 시작 오프셋으로 허용 이동량을 계산하고, 이미지 끝이 드러나기 전에 다음 구간으로 전환한다. 긴 반복 스크롤이 필요해지면 그때 이어 붙일 수 있는 배경을 별도로 제작한다.
표현 규칙 — 제안
캐릭터 발 기준점을 도로 위의 공통 위치에 고정하고 걷기 프레임만 바꾼다. 선택 방향의 반대로 배경을 이동한다. 분기·전투·보물 처리 중에는 배경을 정지하며, 구간 변경은 짧은 전환으로 연결한다. 몬스터와 상자는 배경에 굽지 않고 별도 오브젝트로 표시한다.
정사영 카메라와 2D 스프라이트를 사용하고, 실제 충돌 지형이나 자유 이동 카메라는 두지 않는다. 렌더링을 쉬거나 과거 연출을 생략해도 서버 상태와 보상은 변하지 않는다. 고정 배율 2는 더 큰 렌더링 버퍼를 뜻하며 원본 이미지에 없는 세부를 생성하는 기능은 아니다.

WebSocket은 연결을 통해 서버와 클라이언트가 메시지를 주고받는 통신 수단이다. 연결 자체가 게임을 진행시키거나 메시지의 영구 저장을 보장하는 것은 아니다. 확정 기록과 재접속 동기화는 게임 서버가 담당한다. [T5]
이벤트 기반 지속 진행
게임 서버는 이동·전투 타격·선택 마감 등 다음 사건을 예약한다. 처리 시점이 되면 현재 상태를 읽고 난수 결과를 결정해 저장한 뒤 다음 사건을 예약한다. 60FPS로 모든 캐릭터를 갱신할 필요는 없다. UI 애니메이션 프레임 수와 게임 사건 빈도는 분리한다.
초기에는 하나의 스케줄러가 상태 변경과 예약을 관리한다. 예약 데이터에는 캐릭터 ID, 사건 종류, 실행 시각, 버전을 둔다. 배율·상태가 바뀌면 이전 버전 예약을 무효화한다. 서버가 실행된 동안 발생한 결과는 로그인하지 않은 캐릭터도 계속 저장한다.
한 번 확정된 결과는 바꾸지 않기
제안: 캐릭터 단위로 사건과 명령의 처리 순서를 직렬화하고, 캐릭터 상태·보상·아이템·사건 기록을 같은 DB 트랜잭션에 저장한다. 아이템 판매나 장비 변경 경합에는 행 잠금 또는 버전 검사를 사용한다. PostgreSQL의 행 잠금은 경쟁하는 갱신을 조정하는 수단으로 사용할 수 있다. [T6]
커밋이 끝난 결과만 화면에 확정 알림을 보낸다. 동일한 사건 ID나 요청 ID가 다시 들어오면 재지급하지 않는다. 최초 단계에 분산 마이크로서비스, 별도 메시지 브로커, 복잡한 월드 동기화 엔진을 필수로 넣지 않는다.

재접속 동기화
서버는 현재 상태 스냅샷과 기준 사건 순번을 함께 보낸다. 클라이언트는 그 이후의 확정 이벤트만 순서대로 반영하고 중복 순번은 무시한다. 누락된 구간이 있으면 서버 기록에서 보충하거나 최신 스냅샷을 다시 받는다. 브라우저가 지나간 모험을 새로 계산하지 않는다.
오래된 전투·레벨업 애니메이션을 전부 재생하지 않고 최근 기록 요약과 현재 장면으로 복귀한다. 많은 보상 알림이 쌓여도 모험이 과거 장면에 갇히지 않게 한다.

캐릭터 1개, HOME 1개, 기본 테마 1개로 서버와 화면을 연결한 뒤 나머지 두 테마를 추가한다. 단순한 몬스터·보물·장비 데이터로 먼저 전체 흐름을 완성한다. 게임 창, 상태/장비, 인벤토리, 분기, 로그를 기본 창으로 구성한다.
이번 범위에 넣지 않는 것
동서남북 탐험, 이전 구간 재방문, 수동 이동·플랫폼 액션, 복잡한 공격 애니메이션, 직업별 스킬 트리, PvP, 거래소, 파티·길드, 광역 멀티플레이 월드와 생성형 AI 의사결정은 초기 범위 밖이다. 이는 단순한 자율 모험을 검증하기 위한 범위 통제이며 영구적인 배제 선언은 아니다.
작업 우선순위
첫째는 접속 여부와 무관한 실제 서버 진행, 둘째는 실시간 장비 관리, 셋째는 자유 배치 UI다. 다량의 캐릭터·배경 제작보다 이 세 가지가 한 흐름으로 연결되는지 먼저 확인한다. 테스트와 리팩터링도 해당 단계의 변경 범위와 핵심 실패 경로에 집중한다.
일정·비용 산정의 선행 조건
참여 인력, 목표 배포 환경, 지원 기기, 동시 모험 캐릭터 수와 아트 제작 범위를 정한 뒤 M1·M2 실측으로 기간과 비용을 산정한다. 이 문서에 근거 없는 출시일이나 서버 수용량을 약속하지 않는다.

운영·성능과 주요 위험
서버 상시 진행의 비용은 접속 중인 사용자만이 아니라, 전체 모험 캐릭터의 사건 빈도에서 발생한다.
운영 구조 — 제안
단일 실행 주체와 영속 DB로 시작하고, 예약 지연·실패율·DB 응답·디스크 사용량을 관측한다. 이벤트 처리 결과와 오류를 남기되 걷기 프레임이나 반복 화면 갱신을 서버 로그로 저장하지 않는다. 전체 로그는 보관 기간을 두고, 장기 기록은 요약·집계로 줄인다.
운영 도구에는 서버 진행 상태, 캐릭터별 현재 사건, 예약 지연, 최근 오류, 저장 버전과 접속 모드 조회가 필요하다. 백업과 복구를 실제로 시험하고, 배포 시에는 상태를 저장한 뒤 새 프로세스가 이어받도록 한다. 장애 시간을 사후 보상할 정책은 현재 채택하지 않는다.
부하를 계산하는 기준
기본 사건 처리량은 대략 모험 중 캐릭터 수 ÷ 평균 사건 간격으로 시작해 산정한다. 전투 타격, 분기 마감, 장비 명령과 DB 쓰기를 추가로 계산한다. 예를 들어 1,000개 캐릭터가 평균 5초마다 사건을 만들면 기본 사건만 약 200건/초다. 이는 산술 예시이며 실제 서버 수용량이나 확정 규모가 아니다.
